# Polterware Dispatch Agent Instructions

## Communication and editing

- Speak to Erick in Brazilian Portuguese.
- Write code, UI strings, technical documentation, commits, logs, and identifiers in English. No Portuguese text anywhere in the repository: code, comments, UI strings, error and log messages, tests, fixtures, docs, and skills.
- Preserve unrelated work and make the smallest safe change.
- Do not create branches or commits unless explicitly requested.
- Do not run browsers, previews, or development servers unless the current task asks for them. Automated tests and builds may run by default. Do not open a built `Dispatch.app`: it registers `dispatch://` with LaunchServices.

## Layout

- `crates/dispatch-core`: the `dispatch` core and CLI in Rust (`dispatch_core::cli`, `dispatch_core::server`).
- `app`: the desktop app in GPUI (`dispatch-app`), which is also the `dispatch` binary: given a command, or run as `dispatch` (`Contents/Resources/dispatch` links to it), its `main` runs the CLI and the core instead of the window. Shared controls come from `polterware-ui` (git dependency on [polterware/ui](https://github.com/polterware/ui); a sibling checkout replaces it through a `.cargo/config.toml` `[patch]`). Interface work follows polterware-ui's `AGENTS.md` (Building interface): build the control in polterware-ui as a general component, with the old Solid app's look on our tokens and materials and gpui-kit's behavior, and keep here only Dispatch's data, words, and effects. A control never defers its own panel.
- `schemas`: the contracts. Polterware vendors `dispatch/v1` and `polterware/local/v1/dispatch_host.proto` with its `tooling/sync-dispatch-proto.sh`, so a change here reaches it through that script.
- `tooling`: `verify.sh`, `check-boundaries.sh`, `models.mjs`, `classify-eval.mjs`, `release/bundle.sh`, and `updater` (Sparkle; `configure-secret.sh` exports the signing key and needs Erick's explicit go-ahead).
- `app/resources`: `dispatch.icon` (Icon Composer), the bundle's icon, which `release/bundle.sh` compiles with `actool`, and `dispatch Exports`, its PNG exports from Icon Composer (Default, Dark, Clear, and Tinted). `dispatch-icon.png`, the Dock icon of an unbundled build, and `docs/assets/icon.png` are the Default export on the macOS icon grid (824 px in 1024, transparent around it): `sips -z 824 824 "app/resources/dispatch Exports/dispatch-iOS-Default-1024@1x.png" --out /tmp/icon.png && sips -p 1024 1024 /tmp/icon.png --out app/resources/dispatch-icon.png`.
- `docs/assets`: the icon, the README banner, and the cover (the repository's social preview).
- `updates/dispatch.xml`: the Sparkle appcast.

## Designing for every user

Dispatch is a product for anyone who runs coding agents, not a tool for the Polterware workspace. When a problem shows up in our own use (a failed run, a missing feature, a limit we hit), state it and solve it as it would appear for any user, any repository layout, any language, and any build system. Our setup is one example, never the requirement: do not shape a feature or a recommendation around its specifics (a monorepo question, a Cargo setting, our folder of sibling repositories), and do not answer a Dispatch problem by changing how our projects are organized. Check a design against other cases first (a single repository, several unrelated repositories, a folder with no git, Node or Python projects, one user or many runs at once); an answer that only works here is not the answer.

## What Dispatch does

Polterware Dispatch delegates a task to a coding-agent CLI by difficulty and quota. It is its own local-first app: the `dispatch` binary and core (`crates/dispatch-core`, linked into the app's one binary; `dispatch serve` is the only process that opens `$PWDISPATCH_DATA_DIR/dispatch.db`, else `~/Library/Application Support/Polterware Dispatch/dispatch.db`), its contracts (`schemas`, `dispatch.v1`: DispatchService, WorkspaceService, HealthService; Polterware vendors them), and its desktop (`app`, the GPUI app `dispatch-app` on [polterware/ui](https://github.com/polterware/ui), URL scheme `dispatch://`; the app is named Dispatch, `Dispatch.app`, while its data folder, userData, and Keychain service keep the name Polterware Dispatch, and it updates through Sparkle from `updates/dispatch.xml`, checking daily and from Dispatch › Check for Updates…), which reads the core over Connect-JSON (`app/src/client.rs`) and never opens SQLite. A call waits 4 s for its answer, except the ones that wait on something outside the core (an agent CLI, a classifier, Polterware, or git: `SLOW_PROCEDURES`, 90 s), since a core that has just started asks every agent CLI before the catalog answers. A page that needs several answers asks for them at once (`at_once` and `each_at_once` in `app/src/client.rs`, eight at a time): the sidebar's sections, each workspace's runs, and the open run's reply; Settings' agents and models; Roles' tiers and roles, with its tier check and agents started beside them. The sidebar's runs are read per workspace: the core lists runs by workspace or conversation, never all at once. A `dispatch` command other than `serve` ends quietly by SIGPIPE when its reader closes (`dispatch runs | head`) instead of panicking, which a release build turns into a crash report. It reads Polterware only through `DispatchHostService` (`schemas/polterware/local/v1/dispatch_host.proto`, which Polterware serves; the client is `crates/dispatch-core/src/host`, and `tooling/check-boundaries.sh` holds that nothing here imports Polterware's code) and works on folders alone without it. A workspace is a Polterware project (linked, with the project's id) or a folder added on its own (`dispatch workspace add`, or the folder `dispatch run` starts in). History starts empty: the first start copies the tier table and the routing policy from Polterware. `dispatch serve` adopts the login shell's PATH first (`$SHELL -l -i`), then its own and the usual install folders, so a core the app starts from the Finder finds the agent CLIs a terminal finds; it also resets the signal mask, SIGCHLD, and the macOS background priority it inherits (`reset_inherited_state` in `cli/serve.rs`: the app starts it from a background thread, and a core started with that state never heard its agents exit, so its runs stayed pending). The app starts a core when none answers, the way every CLI command does (`start_core` in `app/src/state.rs`, at most once every 30 s, its output in the core's log); the core is a process of its own, so a run goes on, and ends, with the app closed. A command from a newer build replaces a core from an older one (`ensure_with_exe` in `coreclient/lifecycle.rs`), except while that core reports runs still working (`CheckResponse.active_runs`): stopping it would orphan them, so it stays until it is idle. Checks run through `bash tooling/verify.sh`.

Each run records its calling conversation in `conversation_id`, separate from the worker's resume session: `DISPATCH_CALLER_SESSION` + `DISPATCH_CALLER_AGENT` first (exported by Dispatch's SessionStart hook: to `$CLAUDE_ENV_FILE` where the agent gives one, as Claude Code does, or in Cursor's hook answer `env`), then `POLTERWARE_SESSION` + `POLTERWARE_AGENT_LABEL`, then Codex's `CODEX_THREAD_ID` or `CODEX_SESSION_ID`, then OpenCode's `OPENCODE_SESSION_ID` (so a `dispatch run` from an OpenCode shell lists under that chat), then the nearest known or configured agent ancestor keyed by PID and start time, else empty. Global custom sections store ordered conversation or run references, each in at most one section; `dispatch runs --conversation <id>` filters runs by conversation, across every workspace unless `--project` narrows it.

Where a run came from is its `origin` (`app` or `delegated`), read off `caller_agent` and never stored: a request from the desktop app (it names itself `Polterware-Client: dispatch-desktop`) records the caller `dispatch` and, for a New-page run, a conversation id of its own (`dispatch:<uuid>`), while a follow-up sends none and keeps its run's, and every run an agent starts with the CLI records that agent. A run from an older app, which sent no caller, reads as delegated. Each run gets a folder of its own under the data directory's `artifacts/<run id>/`, exported to every agent as `DISPATCH_ARTIFACTS_DIR` and named in the brief only when the run asks for images (`StartRunRequest.images`, `dispatch run --images`: routing keeps only agents whose `Capabilities.images` says they make images, else it fails with "no image-capable agent installed", and the run records `images`); as a run ends the core indexes the png, jpeg, webp, and gif files it finds there and among its changed files (`worktree::file_changes` against its base, by extension and then by magic bytes), copying the latter into `worktree/<path>` of the run's folder so a cleaned worktree keeps them, with each image's width and height read from its header, into `dispatch_artifacts` (migration 0014: run, workspace, conversation, caller agent, agent, model, repository, path, kind, size, dimensions, and time; `crates/dispatch-core/src/artifacts`). `DispatchService.ListArtifacts` lists them newest first, filtered by origin, repository, agent, conversation, and a search over the making run's prompt, paged with `limit` and `offset` beside the total the filters match, each with the absolute path of its copy; `DeleteArtifact` removes one row and its copy; deleting a run deletes its artifacts, rows and copies. `dispatch artifacts [--origin app|delegated] [--repo <folder>] [--agent <name>] [--conversation <id>] [--query <text>] [--limit <n>] [--offset <n>] [--json]` lists them.

## Spend, stats, the line, and runs across repositories

- Spend and Stats read `dispatch_run_history`, a copy of every run that SQLite triggers keep current on each write (migration 0009) and that no delete touches, so removing a run, a conversation, or a repository never takes its spend or stats with it. Both pages filter by Repository (the run's folder, or below it, whatever workspace it was recorded under), every repository while none is picked; Stats has no other page filter. A run still working counts toward spend as live, its usage read from its agent log (`runner::usage_with_log`), and an orphan keeps what its log says it used. An attempt no price covers leaves the others' cost, marked partial (`Usage::cost_partial`), rather than voiding the run's.
- A writable run that would edit a folder another run is editing in place waits in line instead of failing: it is recorded PENDING with a note naming the run in front (`waiting for run …`), starts by itself once no run started before it is editing that folder, and can be cancelled while it waits. The app says so in a toast when it starts.
- `--with a,b` (`StartRunRequest.with`) names other repositories a task spans: each gets a worktree on the run's branch name (`Run.linked`), committed with the run's, merged with it as one after every branch passes the conflict check, and cleaned with it. Dispatch never edits build files to link them: the agent is told where they are (the prompt and `DISPATCH_LINKED_WORKTREES`), and a repository's own `.dispatch/hooks/link` runs in each worktree once all are cut. A finished run notes files it changed that another open run changed too, before either merges.

## Verification

Run `bash tooling/verify.sh` after relevant changes: `buf lint`, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets`, `cargo test --workspace`, and the boundary check. The live classifier checks: `TYPESAFE_API_KEY=… cargo test -p dispatch-core --test classifier_http live_jev -- --ignored` and `OPENAI_API_KEY=… cargo test -p dispatch-core --test classifier_http live_openai -- --ignored`.

End to end, each test runs the built binary in a home, data folder, and git repository of its own (never the user's), with a fake ACP agent (`crates/dispatch-core/tests/fixtures/e2e/fake-acp.sh`: a prompt with WRITE writes `e2e.txt`, SLOW waits 60 s, FAIL errors, and `FAKE_ACP_LOG` records what it was sent) as the only allowed agent. `crates/dispatch-core/tests/e2e_cli.rs` drives the CLI and the core (runs read-only and writing, merge, clean, fallback after a failure, cancel, orphan and recover, the core restarted, roles, config, global only, workspaces, agents, sections, setup's skills and hooks, and a core started from a background thread, output into a closed pipe); `DISPATCH_E2E_BIN` runs it on another build. In the app, `app/tests/client_e2e.rs` calls every RPC the pages use through `app/src/client.rs`, and `app/tests/ui_flows.rs` opens the real window in gpui's `TestAppContext` (`test-support`, one test at a time) and clicks through it: every page with data, ⌘K, ⌘, (open and close) and Back, Merge then Delete worktree, Cancel from the runs page, Settings' hook, skill, and routing switches, and its Priority and classifier model pickers. Its clicks find elements by `debug_selector`, which polterware-ui's `Button`, a labelled `Switch` row, a `Menu` row (`menu-item-<index>`), and the settings dialog's `settings-content` carry by id; springs run on the real clock and step only when the window draws, so a test pumps frames (`pump`) after one opens or closes something; gpui keeps an element's bounds from earlier frames, so a test checks what the app holds, not that an element is gone, and its clock moves only when the test advances it. `crates/dispatch-core/tests/e2e_live.rs` is ignored: it runs the real agents on their cheapest models and Jev's classifier and Auto routing, spending a little quota and one Jev request (`cargo test -p dispatch-core --test e2e_live -- --ignored --test-threads=1`; `DISPATCH_LIVE_MODELS=agent/model,…` picks them, and `DISPATCH_E2E_BIN` another build to run).
