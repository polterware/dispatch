## Layout

- `crates/dispatch-core`: the `dispatch` core and CLI in Rust (`dispatch_core::cli`, `dispatch_core::server`); it embeds the OpenCode plugin files.
- `app`: the desktop app in GPUI (`dispatch-app`), which is also the `dispatch` binary: given a command, or run as `dispatch` (`Contents/Resources/dispatch` links to it), its `main` runs the CLI and the core instead of the window. Shared controls come from `polterware-ui` (git dependency on [polterware/ui](https://github.com/polterware/ui); a sibling checkout replaces it through a `.cargo/config.toml` `[patch]`). Use no third-party GPUI kit, and a control never defers its own panel.
- `schemas`: the contracts. Polterware vendors `dispatch/v1` and `polterware/local/v1/dispatch_host.proto` with its `tooling/sync-dispatch-proto.sh`, so a change here reaches it through that script.
- `plugins/opencode-gui`: the OpenCode Desktop plugin (Solid), with the bot avatars vendored under `vendor/bot-avatars` (MIT).
- `tooling`: `verify.sh`, `check-boundaries.sh`, `models.mjs`, `classify-eval.mjs`, `render-icon.swift` (renders `app/resources/dispatch.icon` to a PNG: the Dock icon of an unbundled build, `app/resources/dispatch-icon.png`, and `docs/assets/icon.png`), `release/bundle.sh`, and `updater` (Sparkle; `configure-secret.sh` exports the signing key and needs Erick's explicit go-ahead).
- `docs/assets`: the README's icon, cover, and banner.
- `updates/dispatch.xml`: the Sparkle appcast.

## What Dispatch does

Polterware Dispatch delegates a task to a coding-agent CLI by difficulty and quota. It is its own local-first app: the `dispatch` binary and core (`crates/dispatch-core`, linked into the app's one binary; `dispatch serve` is the only process that opens `$PWDISPATCH_DATA_DIR/dispatch.db`, else `~/Library/Application Support/Polterware Dispatch/dispatch.db`), its contracts (`schemas`, `dispatch.v1`: DispatchService, WorkspaceService, HealthService; Polterware vendors them), and its desktop (`app`, the GPUI app `dispatch-app` on [polterware/ui](https://github.com/polterware/ui), URL scheme `dispatch://`; the app is named Dispatch, `Dispatch.app`, while its data folder, userData, and Keychain service keep the name Polterware Dispatch, and it updates through Sparkle from `updates/dispatch.xml`, checking daily and from Dispatch › Check for Updates…), which reads the core over Connect-JSON (`app/src/client.rs`) and never opens SQLite. It reads Polterware only through `DispatchHostService` (`schemas/polterware/local/v1/dispatch_host.proto`, which Polterware serves; the client is `crates/dispatch-core/src/host`, and `tooling/check-boundaries.sh` holds that nothing here imports Polterware's code) and works on folders alone without it. A workspace is a Polterware project (linked, with the project's id) or a folder added on its own (`dispatch workspace add`, or the folder `dispatch run` starts in). History starts empty: the first start copies the tier table and the routing policy from Polterware. `dispatch serve` adopts the login shell's PATH first (`$SHELL -l -i`), then its own and the usual install folders, so a core the app starts from the Finder finds the agent CLIs a terminal finds. Checks run through `bash tooling/verify.sh`.

Each run records its calling conversation in `conversation_id`, separate from the worker's resume session: `DISPATCH_CALLER_SESSION` + `DISPATCH_CALLER_AGENT` first (exported by Dispatch's Claude Code SessionStart hook), then `POLTERWARE_SESSION` + `POLTERWARE_AGENT_LABEL`, then Codex's `CODEX_THREAD_ID` or `CODEX_SESSION_ID`, then OpenCode's `OPENCODE_SESSION_ID` (so a `dispatch run` from an OpenCode shell lists under that chat), then the nearest known or configured agent ancestor keyed by PID and start time, else empty. Global custom sections store ordered conversation or run references, each in at most one section; `dispatch runs --conversation <id>` filters runs by conversation, across every workspace unless `--project` narrows it.

The app does not start runs: agents start them with `dispatch run` (the skill, or the CLI in a repository), and Polterware's Commander starts them through the core; the app follows, merges, and tunes them. The window has no frame: the sidebar and the empty parts of the chrome (a page toolbar, a run's header, the empty page, the main surface's top 44px) drag it through polterware-window's window drag, and a double click zooms. Its sidebar reads like a chatbot's: Commander (⌘K: each page, Settings, and Reload, which reads every page and the sidebar again) and the pages Roles, Intelligence, Spend, and Stats on top (they show with no workspace or run yet), then collapsible run groups, by the conversation that started them by default (the chat's earliest prompt names it and its caller agent's bot leads it; runs with no conversation fall under Other runs), listing runs by their prompt's first line with a status dot (a long hover opens the run's transcript as it streams in a `HoverCard` on the right); the Runs header's Display menu groups by Conversation, Workspace, Date, Status, Agent, or None, sorts by Last updated, Date created, or Name in either direction, and shows All runs, Hide merged, or Running and needs merge (the display and collapsed groups stay on this computer); custom sections (`DispatchService.ListSections|SaveSection|DeleteSection|MoveToSection`) come first, are created from New section and renamed or deleted from their "…", and take a run or a whole conversation from its right-click menu; Reset to defaults restores the display and View all opens the runs list with its filters, and Settings in the footer; the app opens on Roles, and the runs page with no run open says how runs start; a run opens in the page structure of docs (`rail_page`), in two columns: the transcript alone in the center, set the way the agent's terminal prints it from its JSON stream, live as it arrives (Codex over `codex app-server`, the protocol the Codex apps use, whose notifications stream reply and reasoning deltas, command output, and items as they start, one compact line each in the live log; Claude Code `stream-json` with partial messages (the prompt on stdin; plan permission mode when read-only, acceptEdits otherwise), Pi `--mode json` (a read-only run keeps only its read, grep, find, and ls tools), and the Agent Client Protocol, JSON-RPC over stdio, for OpenCode (`opencode acp`), Antigravity (`agy acp`), Gemini and Qwen (`--acp`, `--approval-mode plan` when read-only), Copilot (`--acp`), Kimi (`kimi acp`), and any ACP agent added with `dispatch agents add <name> -- <command…>` (`dispatch agents remove <name>`; the global config's `acp_agents` only, never a repository's): `session/update` lines, the agent's read mode where it has one (OpenCode's plan agent is required, because its build agent edits without asking), and every permission request refused in a read-only run but read, search, fetch, and think; Cursor `stream-json` and Grok `streaming-json`; Claude models run only in Claude Code; `build_transcript` in `app/src/models/transcript.rs`, drawn by `app/src/ui/parts/transcript.rs` in JetBrains Mono with syntect on the app's palette): tool calls as `›` steps with the command highlighted as shell and the first lines of its output, reasoning dimmed, the reply as terminal Markdown with highlighted code, other CLI output with terminal escapes stripped (diffs and JSON highlighted), and the core's `[kind] …` lines as `✓ merged …` rows; the stored final reply closes a transcript whose stream holds none; and the rail on the right, on a card (`rail_card`), with its Agent (its bot, animated while the run works, agent / model / provider, and any failed attempts before it), Prompt, Run, Routing (the decision's policy, the task's `d`, band, and area, the role and how it came (picked with its P, general, or named by the request), and each candidate in routing order with P(pass), its bound, effective cost, and quota multiplier, the one tried first marked; `DispatchService.GetRouteDecision`, hidden for a run with no decision), Changes (files, branch, worktree, merge commit; the core keeps the counts, not the patch), and Linked runs groups, each collapsing from its heading (`RailGroup`). The header has Back and the next step, with no status chip: Merge for a finished run with a worktree that is not merged (`DispatchService.MergeRun`, which merges the worktree branch directly and keeps the worktree, then offers Delete worktree; `dispatch merge` removes it in one step; revert the merge commit to undo it), Cancel while it runs; its "…" menu holds Recover run (an interrupted run) and Remove worktree (`RecoverRun`, `CleanRun`). There is no Verify. Intelligence (`DispatchService.ListModelCatalog`, tab id `models`) is about skill only, with no cost or quota: a table of the tier table's models and every model the installed agent CLIs report (`ListModels`), the latter marked Found while `discover` is on (the default), so Auto routes to them, else Installed: ordered by skill: a Score (100·σ(θ), in the `segment_display`), model and agent, θ with its source and the benchmark figure (CursorBench 62%, ECI 141, Tier strength, or Unknown), P(pass) and its lower bound at easy, normal, and hard (`d` −2.8, −1.8, −0.8), bright where the bound meets the policy priority's bar, with the catalog's date and sources below, filtered by Agent, Tier (Found or Installed for a reported model), Skill source, and Meets the bar (the bands whose lower bound meets it); the table is virtualized (`DataTable`, a GPUI uniform list), drawing only the rows in view as it scrolls. Settings has one page per concern: Try a route (`Route`, with a prompt; on Auto each candidate shows P, cost, and the quota multiplier), Classifier (one radio group: Off, the default; Jev (TypeSafe); OpenAI Decisions; or the easy tier's model through an agent CLI, last because it spends quota, naming its agent and model; the picked Jev or OpenAI option opens its key in place: where it is found, never the value, a password field with Save, or Replace and Remove (`Config` `key-set|key-clear`, `dispatch config key set|clear jev|openai`, which reads the key from stdin), and Test, and a keyed option with no key reads Needs a key; then Pick a role (the `roles` switch, on by default) and Classify a prompt (`Classify`: the classifier's P(easy), P(normal), P(hard), the tier, `d`, and the role it picks with P per role), and Routing policy, global or the project's (`Config`: priority, discover, and the allow and deny lists as tokens, offering the agents and the providers and models their CLIs report, or any typed value). Agents (opened first and from Commander's Agent setup) is how the agent CLIs reach dispatch, which they use through the CLI and the skill, never MCP (`DispatchService.GetAgentSetup|ApplyAgentSetup`, `dispatch setup [--json] | link | skill [<agent>] | hook on|off`, `crates/dispatch-core/src/setup`): the `dispatch` command at `~/.local/bin/dispatch` (Linked to the app's binary, Another copy, or Not installed; Install or Replace links it), the skill per skills folder (Codex and Grok share `~/.agents/skills`; Current, Outdated, or Not installed; Install, Update, or Install for all), and the Claude Code SessionStart hook as a switch, with Point to this app when it runs another binary; then the OpenCode plugin (`dispatch setup opencode [--remove | on | off]`, `install_opencode|remove_opencode|opencode_on|opencode_off`; Install, Update, Remove, and a delegation switch), files in `crates/dispatch-core/src/setup/opencode` installed into the state directory's `opencode-plugin` and loaded by one `plugins` entry in OpenCode's global `opencode.json(c)` (the only edit to that file, comments kept, with the binary and the switch file `opencode-plugin.json` as options). While delegation is on (the default) its server part takes OpenCode's `subagent` tool out of each model call and adds `dispatch_run` (waits unless `wait: false`), `dispatch_wait`, and `dispatch_merge`, each run under the conversation `opencode:<root session>` (with no dispatch binary to run, it keeps the subagent tool); its OpenCode Desktop part (`gui-experimental.cjs`, built from `plugins/opencode-gui` with `pnpm --dir plugins/opencode-gui build` and checked fresh by `tooling/verify.sh`, on the Solid and SDK modules the app provides) adds a composer pill that opens the Dispatch side panel (its label says whether delegation is on and counts the conversation's runs), the switch in that panel's header, Settings › Dispatch, and `/dispatch`; the panel lists the runs, each with its agent's bot, and shows the sleeping Polterware ghost while there are none, a run opening at `dispatch://run/<id>`. A route restricted to OpenCode weighs every model `opencode models` lists, and a tier with no OpenCode entry takes the ones `BuildTiers` ranks for it; `dispatch tiers build --agent <a> [--apply]` builds, or replaces, one agent's entries. Roles (tab id `roles`; the `tiers` and `subagents` ids open it) is the page of the kinds of work a run does. It opens on a list, a 44px `DataTable` (Role, When to use, Tier, Access, Models, Source) with General first and then each role, under a switch for the pick and with New role in the toolbar; a row opens that role's board, whose toolbar has Back and its name, then Build from model (General only) or Edit role. General is the tier table, a board: one column per tier, one row per order position (row 1 is the primary, the rest fallbacks); cards move by pointer drag, and each tier's first empty cell is Add model, which opens a popover anchored to it that lists the models the installed agent CLIs report (`DispatchService.ListModels`; each CLI's list stays fresh five minutes and is kept in the state directory's `agent-models.json` across restarts, an older one answers at once while the CLI is asked again behind it, and a CLI that cannot list is kept as such too, so it holds up one read, not every one), plus a custom agent and model pair; a pick lands in that cell. There is no toolbar +. Every edit replaces the stored table through `DispatchService.ReplaceTiers`, which validates it like `tiers.json`. Build from model, a labeled button at the toolbar's start, opens a Peek with the table the model catalog proposes (`DispatchService.BuildTiers`, `dispatch tiers build [--apply]`): for each tier's typical difficulty, up to three of the stored and discovered models, one per base model, weighing every supported effort and keeping its best one like Auto, with P(pass) and cost; Apply stores it, and the board stays editable. Every other role (through the core's `Subagents` RPC: list, check, save, remove) shows its When to use, instructions, access, lowest tier, and source (Built in, Yours, From the repository; Only with --role for a manual one) and the same board of its own, saved on each edit, whose empty tiers run on General's; Edit role and New role open the composer (name, instructions, Lowest tier, Access, Picked, Prefer, and Avoid pills, When to use and Time limit fields, Restore built-in or Remove role). Built in are explorer, implementer, tester, reviewer, and planner; the user's `roles.json` in the state directory and a repository's `.dispatch/roles.json` add or replace them by name (an `agents.json` beside them, which an earlier Dispatch wrote, is read until a save writes `roles.json`; a copy with no `when` keeps the built-in one's; removing the user's copy restores the built-in); `dispatch roles [--check] | save <name> [--when …] [--tier …] [--easy|--normal|--hard agent/model,…] [--readonly] [--manual] … | remove <name>`, and `general` and `none` are reserved. Role and difficulty combine: the role picks the board and the difficulty its column. On an Auto run that names no role, with the `roles` policy on (the default), the classifier picks one in the same call that judges difficulty (Jev a `choice` question over each pickable role's `when` plus general; the CLI classifier a `role` in its JSON; OpenAI Decisions picks none): the most likely role at P ≥ 0.5, else general, which keeps the plain route. A role, named with `--role` or picked, adds its instructions, timeout, priority, agent, and prefer and avoid, and its tier is a floor on `d` (with no classifier, on the normal tier), never a fixed tier; a picked role never makes a run read-only (access changes only with `--readonly` or `--role`) and never pins a model or provider. A run whose role has models in the run's band routes over those alone, in board order, as a tier route of that band (no tier table, no discovery); an empty band takes General's route. The run keeps the pick and its P per role (`role_json`), shown in the run's Routing group and in `dispatch route`; `--role none` runs with no role and no pick. Spend (tab id `usage`) holds what Dispatch costs: a 44px `DataTable` with filters for Provider, Quota (Available, Low at 90% used, Cooldown, Unknown), Pace, Spend window, and Dispatch runs in that window, one row per agent whose CLI is on this machine (`DispatchAgent.installed`; the others are not listed), with its bot, the used percentage as a `SegmentDisplay` (where the number comes from is its tooltip), pace, window and reset, and Cost / task (the cheapest to the dearest of its catalog models, each model's price and source as the tooltip), then what runs through Dispatch spent over the filter's Spend window (24 hours, 7 days by default, 30 days, all time), summed across every workspace: Tokens (input, cache, output, and reasoning as its tooltip) and API cost. A run's usage is read from its agent CLI's stream (Codex `thread/tokenUsage/updated`, Claude Code `result` with its `modelUsage`, every model the run called, a subagent's included, else each call's `message_delta`, Pi each assistant `message_end`, an ACP agent's prompt response, whose input counts the cache or not as its total says, and its `usage_update`, Cursor `result`, Grok `end`), with how full the context window was after the last model call and the window's size where the CLI says it (Codex, Claude Code, ACP `usage_update`, else the catalog's), summed over its attempts, and stored on the run (`usage_json`); its cost is the API-equivalent price, not what a subscription bills: the CLI's own price where it reports one (Claude Code, Pi, Grok, and an ACP `usage_update` in USD above zero on a session that was not resumed), else the tokens at the catalog's models.dev list prices, cache prices included and the long-context tier's prices past 200k, and unknown when an attempt could not be priced. The run's Run group shows its Tokens, its Context (used of the window, with a bar), and its Cost, live while it runs from the adapter's `{"dispatch":"usage"}` log lines (which the transcript does not draw), and `dispatch status|result|usage` print them; a run from before usage was recorded has none. Stats has no cost, each of its sections (Rankings, the runs chart, the table) folds from its heading (`CollapsibleSection`), and it keeps its cards with no runs (the window's periods at zero, rankings with no answer): rankings, runs over time or by group (Day, Week, Model, Agent, Provider, Tier, or Area, the area read from each run's routing decision), and a table of runs, success, first try, p50, p90, fallbacks, rate limits, and orphans; the benchmarks live in Intelligence alone (the CLI keeps `dispatch models bench`: each model the installed agent CLIs report with its CursorBench score at every reasoning level and its ECI, `as <model>` when a shorter key matched). Worktree info lives on the run page; a run that failed, was cancelled, timed out, or was orphaned shows its own end on the worktree chip instead of "active". Auto exists only with a difficulty classifier (`config set classifier jev|openai|cli`; `crates/dispatch-core/src/classifier`): with none, a run with no tier, model, or provider takes the normal tier, `--tier auto` is refused, and Auto is not offered in the app. The classifier reads the card the run names (title, intent, tasks, questions, invariants; no handoff) and then the prompt, and answers P(easy), P(normal), P(hard) (Jev at `api.typesafe.ai/v1/systemone`, OpenAI at `/v1/decisions`, keys from `TYPESAFE_API_KEY` or `OPENAI_API_KEY`, else the macOS Keychain: a generic password under service `Polterware Dispatch`, account `jev` or `openai`, accessible when unlocked on this device only, that the `dispatch` binary saves and reads through Security.framework, whose access list trusts only that binary, so `security` and any other program have to ask (an item an earlier Dispatch saved through `security` is read once and saved again natively); `~/.config` key files are not read, the keys are never in SQLite, and the value is never reported) or only a tier (the CLI); the tier is hard at P(hard) ≥ 0.2, normal at P(normal)+P(hard) ≥ 0.35, else easy, and `d` is the expected band midpoint kept inside that band. A classifier that fails leaves the run on the normal tier with a note. Auto (`--tier auto`, or no tier, model, or provider with a classifier on) routes across every tier's entries and the discovered models (`discover` is on by default), weighing each model at every supported effort and keeping its best one: `P(pass) = σ(θ − d)`, with the task's difficulty `d` from the classifier and each model@effort's `θ` from the embedded catalog (`models_snapshot.json`, from CursorBench and the Epoch Capabilities Index by `tooling/models.mjs`, prices from models.dev; `dispatch models [refresh|bench]`, `DispatchService.ListModelCatalog|RefreshModelCatalog|ListModelBenchmarks`), else tiers.json strength, else a mid-field θ (−0.7, its cost the catalog's median); nothing is learned from runs, so every number traces to the catalog, the classifier, or the CLIs' quota. The lower bound is σ(θ − d − u), with u 0.3 for CursorBench, 0.5 for ECI, and 0.8 otherwise, plus 0.1 per extrapolated effort level; the candidates whose lower bound meets the priority's bar (speed 0.70, balanced 0.80, quality 0.90) go by cost × quota multiplier, the rest by bound, and the run records the band of `d` as its tier. A tier route (a tier and no model, agent, or provider) tries its table in order and passes over an account whose quota is low (90% used, or projected to run out before it resets) for the next entry, with a rate-limited one last and, when every account is low, the one with the most left first; unknown quota is not low, and the priority does not reorder it. A tier or model route is priced by the catalog too (policy `tier-v2`), with a note when its first candidate falls under the bar. Every new run logs its routing decision without the prompt (`dispatch_route_decisions`, with its area), shown in the run's Routing group. A dispatch run is a core-executed delegation in `crates/dispatch-core/src/runner` and belongs to a workspace. In a linked workspace it runs in the request's directory, else the picked repository's clone, else the card's component repository, else the only repository, as Polterware resolves it, and otherwise asks to pick one; it starts a linked AgentRun in Polterware (the audited session its agent writes under, shown in Activity) and may reference a Work card slug. A standalone workspace runs in its folder, and so does a linked one while Polterware is away. The CLI is `dispatch run|runs|wait|result|cancel|status|merge|clean|recover|route|classify|models|tiers|usage|agents|doctor|roles|config|skill|setup|update|on|off|hook|workspace|serve|stop`; there is no TUI. There is no Dispatch MCP tool. Live output stays on the run page. Quota comes only from the CLIs' official protocols; unknown usage stays unknown. Claude Code has no command that reports it, so its quota is the `rate_limit_event` its last run printed (the five-hour and weekly windows' utilization and resets, sampled when Claude printed them; routing reads the one closest to its limit), kept in the state directory's `claude-rate-limits.json` across restarts and unknown before the first run and once a window resets.
