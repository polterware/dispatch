## Layout

- `crates/dispatch-core`: the `dispatch` core and CLI in Rust (`dispatch_core::cli`, `dispatch_core::server`); it embeds the OpenCode plugin files.
- `app`: the desktop app in GPUI (`dispatch-app`), which is also the `dispatch` binary: given a command, or run as `dispatch` (`Contents/Resources/dispatch` links to it), its `main` runs the CLI and the core instead of the window. Shared controls come from `polterware-ui` (git dependency on [polterware/ui](https://github.com/polterware/ui); a sibling checkout replaces it through a `.cargo/config.toml` `[patch]`). Interface work follows polterware-ui's `AGENTS.md` (Building interface): build the control in polterware-ui as a general component, with the old Solid app's look on our tokens and materials and gpui-kit's behavior, and keep here only Dispatch's data, words, and effects. A control never defers its own panel.
- `schemas`: the contracts. Polterware vendors `dispatch/v1` and `polterware/local/v1/dispatch_host.proto` with its `tooling/sync-dispatch-proto.sh`, so a change here reaches it through that script.
- `plugins/opencode-gui`: the OpenCode Desktop plugin (Solid), with the bot avatars vendored under `vendor/bot-avatars` (MIT).
- `tooling`: `verify.sh`, `check-boundaries.sh`, `models.mjs`, `classify-eval.mjs`, `release/bundle.sh`, and `updater` (Sparkle; `configure-secret.sh` exports the signing key and needs Erick's explicit go-ahead).
- `app/resources`: `dispatch.icon` (Icon Composer), the bundle's icon, which `release/bundle.sh` compiles with `actool`, and `dispatch Exports`, its PNG exports from Icon Composer (Default, Dark, Clear, and Tinted). `dispatch-icon.png`, the Dock icon of an unbundled build, and `docs/assets/icon.png` are the Default export on the macOS icon grid (824 px in 1024, transparent around it): `sips -z 824 824 "app/resources/dispatch Exports/dispatch-iOS-Default-1024@1x.png" --out /tmp/icon.png && sips -p 1024 1024 /tmp/icon.png --out app/resources/dispatch-icon.png`.
- `docs/assets`: the icon, the README banner, and the cover (the repository's social preview).
- `updates/dispatch.xml`: the Sparkle appcast.

## What Dispatch does

Polterware Dispatch delegates a task to a coding-agent CLI by difficulty and quota. It is its own local-first app: the `dispatch` binary and core (`crates/dispatch-core`, linked into the app's one binary; `dispatch serve` is the only process that opens `$PWDISPATCH_DATA_DIR/dispatch.db`, else `~/Library/Application Support/Polterware Dispatch/dispatch.db`), its contracts (`schemas`, `dispatch.v1`: DispatchService, WorkspaceService, HealthService; Polterware vendors them), and its desktop (`app`, the GPUI app `dispatch-app` on [polterware/ui](https://github.com/polterware/ui), URL scheme `dispatch://`; the app is named Dispatch, `Dispatch.app`, while its data folder, userData, and Keychain service keep the name Polterware Dispatch, and it updates through Sparkle from `updates/dispatch.xml`, checking daily and from Dispatch › Check for Updates…), which reads the core over Connect-JSON (`app/src/client.rs`) and never opens SQLite. It reads Polterware only through `DispatchHostService` (`schemas/polterware/local/v1/dispatch_host.proto`, which Polterware serves; the client is `crates/dispatch-core/src/host`, and `tooling/check-boundaries.sh` holds that nothing here imports Polterware's code) and works on folders alone without it. A workspace is a Polterware project (linked, with the project's id) or a folder added on its own (`dispatch workspace add`, or the folder `dispatch run` starts in). History starts empty: the first start copies the tier table and the routing policy from Polterware. `dispatch serve` adopts the login shell's PATH first (`$SHELL -l -i`), then its own and the usual install folders, so a core the app starts from the Finder finds the agent CLIs a terminal finds; it also resets the signal mask, SIGCHLD, and the macOS background priority it inherits (`reset_inherited_state` in `cli/serve.rs`: the app starts it from a background thread, and a core started with that state never heard its agents exit, so its runs stayed pending). The app starts a core when none answers, the way every CLI command does (`start_core` in `app/src/state.rs`, at most once every 30 s, its output in the core's log); the core is a process of its own, so a run goes on, and ends, with the app closed. Checks run through `bash tooling/verify.sh`.

Each run records its calling conversation in `conversation_id`, separate from the worker's resume session: `DISPATCH_CALLER_SESSION` + `DISPATCH_CALLER_AGENT` first (exported by Dispatch's SessionStart hook: to `$CLAUDE_ENV_FILE` where the agent gives one, as Claude Code does, or in Cursor's hook answer `env`), then `POLTERWARE_SESSION` + `POLTERWARE_AGENT_LABEL`, then Codex's `CODEX_THREAD_ID` or `CODEX_SESSION_ID`, then OpenCode's `OPENCODE_SESSION_ID` (so a `dispatch run` from an OpenCode shell lists under that chat), then the nearest known or configured agent ancestor keyed by PID and start time, else empty. Global custom sections store ordered conversation or run references, each in at most one section; `dispatch runs --conversation <id>` filters runs by conversation, across every workspace unless `--project` narrows it.

The app does not start runs: agents start them with `dispatch run` (the skill, or the CLI in a repository), and Polterware's Commander starts them through the core; the app follows, merges, and tunes them. The window has no frame: the sidebar and the empty parts of the chrome (a page toolbar, a run's header, the empty page, the main surface's top 44px) drag it through polterware-window's window drag, and a double click on empty area zooms; a double click on a control inside a drag region (a sidebar item or section heading, a button: `window_drag_control`) is the control's and never zooms. Auto exists only with a difficulty classifier (`config set classifier jev|openai|cli`; `crates/dispatch-core/src/classifier`): with none, a run with no tier, model, or provider takes the normal tier, `--tier auto` is refused, and Auto is not offered in the app. The classifier reads the card the run names (title, intent, tasks, questions, invariants; no handoff) and then the prompt, and answers P(easy), P(normal), P(hard) (Jev at `api.typesafe.ai/v1/systemone`, OpenAI at `/v1/decisions`, keys from `TYPESAFE_API_KEY` or `OPENAI_API_KEY`, else the macOS Keychain: a generic password under service `Polterware Dispatch`, account `jev` or `openai`, accessible when unlocked on this device only, that the `dispatch` binary saves and reads through Security.framework, whose access list trusts only that binary, so `security` and any other program have to ask (an item an earlier Dispatch saved through `security` is read once and saved again natively); `~/.config` key files are not read, the keys are never in SQLite, and the value is never reported) or only a tier (the CLI); the tier is hard at P(hard) ≥ 0.2, normal at P(normal)+P(hard) ≥ 0.35, else easy, and `d` is the expected band midpoint kept inside that band. A classifier that fails leaves the run on the normal tier with a note. Auto (`--tier auto`, or no tier, model, or provider with a classifier on) routes across every tier's entries and the discovered models (`discover` is on by default), weighing each model at every supported effort and keeping its best one: `P(pass) = σ(θ − d)`, with the task's difficulty `d` from the classifier and each model@effort's `θ` from the embedded catalog (`models_snapshot.json`, from CursorBench and the Epoch Capabilities Index by `tooling/models.mjs`, prices from models.dev; `dispatch models [refresh|bench]`, `DispatchService.ListModelCatalog|RefreshModelCatalog|ListModelBenchmarks`), else tiers.json strength, else a mid-field θ (−0.7, its cost the catalog's median); nothing is learned from runs, so every number traces to the catalog, the classifier, or the CLIs' quota. The lower bound is σ(θ − d − u), with u 0.3 for CursorBench, 0.5 for ECI, and 0.8 otherwise, plus 0.1 per extrapolated effort level; the candidates whose lower bound meets the priority's bar (speed 0.70, balanced 0.80, quality 0.90) go by cost × quota multiplier, the rest by bound, and the run records the band of `d` as its tier. A tier route (a tier and no model, agent, or provider) tries its table in order and passes over an account whose quota is low (90% used, or projected to run out before it resets) for the next entry, with a rate-limited one last and, when every account is low, the one with the most left first; unknown quota is not low, and the priority does not reorder it. A tier or model route is priced by the catalog too (policy `tier-v2`), with a note when its first candidate falls under the bar. Every new run logs its routing decision without the prompt (`dispatch_route_decisions`, with its area), shown in the run's Routing group. A dispatch run is a core-executed delegation in `crates/dispatch-core/src/runner` and belongs to a workspace. In a linked workspace it runs in the request's directory, else the picked repository's clone, else the card's component repository, else the only repository, as Polterware resolves it, and otherwise asks to pick one; it starts a linked AgentRun in Polterware (the audited session its agent writes under, shown in Activity) and may reference a Work card slug. A standalone workspace runs in its folder, and so does a linked one while Polterware is away. The CLI is `dispatch run|runs|wait|result|cancel|status|merge|clean|recover|route|classify|models|tiers|usage|agents|doctor|roles|config|skill|setup|update|on|off|hook|workspace|serve|stop`; there is no TUI. Every RPC that takes a run (status, result, events, watch, cancel, merge, clean, recover, routing) takes the one run whose id starts with what it is given, from 6 characters on, as `dispatch runs` prints its first 12. There is no Dispatch MCP tool. Live output stays on the run page. Quota comes only from the CLIs' official protocols; unknown usage stays unknown. Claude Code has no command that reports it, so its quota is the `rate_limit_event` its last run printed (the five-hour and weekly windows' utilization and resets, sampled when Claude printed them; routing reads the one closest to its limit), kept in the state directory's `claude-rate-limits.json` across restarts and unknown before the first run and once a window resets.

## Verification

Run `bash tooling/verify.sh` after relevant changes: `buf lint`, the plugin tests, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets`, `cargo test --workspace`, the plugin's typecheck and build check, and the boundary check. Maintain risk-proportional tests. A test that calls a paid or external API is `#[ignore]` and runs only while working on that feature; the default suite uses a local fake instead (`crates/dispatch-core/tests/classifier_http.rs` serves Jev and OpenAI Decisions on 127.0.0.1). The live classifier checks: `TYPESAFE_API_KEY=… cargo test -p dispatch-core --test classifier_http live_jev -- --ignored` and `OPENAI_API_KEY=… cargo test -p dispatch-core --test classifier_http live_openai -- --ignored`.

End to end, each test runs the built binary in a home, data folder, and git repository of its own (never the user's), with a fake ACP agent (`crates/dispatch-core/tests/fixtures/e2e/fake-acp.sh`: a prompt with WRITE writes `e2e.txt`, SLOW waits 60 s, FAIL errors, and `FAKE_ACP_LOG` records what it was sent) as the only allowed agent. `crates/dispatch-core/tests/e2e_cli.rs` drives the CLI and the core (runs read-only and writing, merge, clean, fallback after a failure, cancel, orphan and recover, the core restarted, roles, config, global only, workspaces, agents, sections, setup's skills and hooks, and a core started from a background thread); `DISPATCH_E2E_BIN` runs it on another build. In the app, `app/tests/client_e2e.rs` calls every RPC the pages use through `app/src/client.rs`, and `app/tests/ui_flows.rs` opens the real window in gpui's `TestAppContext` (`test-support`, one test at a time) and clicks through it: every page with data, ⌘K, ⌘, (open and close) and Back, Merge then Delete worktree, Cancel from the runs page, Settings' hook, skill, and routing switches, and its Priority and classifier model pickers. Its clicks find elements by `debug_selector`, which polterware-ui's `Button`, a labelled `Switch` row, a `Menu` row (`menu-item-<index>`), and the settings dialog's `settings-content` carry by id; springs run on the real clock and step only when the window draws, so a test pumps frames (`pump`) after one opens or closes something; gpui keeps an element's bounds from earlier frames, so a test checks what the app holds, not that an element is gone, and its clock moves only when the test advances it. `crates/dispatch-core/tests/e2e_live.rs` is ignored: it runs the real agents on their cheapest models and Jev's classifier and Auto routing, spending a little quota and one Jev request (`cargo test -p dispatch-core --test e2e_live -- --ignored --test-threads=1`; `DISPATCH_LIVE_MODELS=agent/model,…` picks them, and `DISPATCH_E2E_BIN` a build whose Keychain item holds the Jev key, such as the installed app's `Contents/Resources/dispatch`).
